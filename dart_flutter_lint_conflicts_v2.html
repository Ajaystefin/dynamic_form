Dart and Flutter lint rule conflicts and issues, with official references

Direct conflicts — enabling both rules produces contradictory requirements

Rules in conflict Severity Explanation Reference
prefer_double_quotes
vs
avoid_escaping_inner_quotes		 Direct conflict Enforcing double quotes on all strings means any string containing a double quote will need escaping inside it, which the second rule immediately flags. The two rules cannot both pass on the same string. prefer_double_quotes avoid_escaping_inner_quotes
always_specify_types
vs
avoid_types_on_closure_parameters		 Direct conflict One rule requires an explicit type annotation everywhere, including on closure parameters. The other rule specifically prohibits type annotations on closure parameters. There is no way to satisfy both at once. always_specify_types avoid_types_on_closure_parameters
always_specify_types
vs
omit_local_variable_types		 Direct conflict One rule requires an explicit type on every local variable. The other requires the type to always be omitted on local variables. Both cannot be satisfied at the same time. always_specify_types omit_local_variable_types
always_specify_types
vs
omit_obvious_local_variable_types		 Direct conflict When the type of a local variable is obvious from context, the second rule requires it to be omitted, which puts it in direct opposition to always_specify_types. always_specify_types omit_obvious_local_variable_types
prefer_final_parameters
vs
avoid_final_parameters		 Direct conflict These two rules are exact opposites. One requires every parameter to be marked final; the other forbids it. Every parameter in the codebase will trigger a warning from one of them. prefer_final_parameters avoid_final_parameters
prefer_expression_function_bodies
vs
always_put_control_body_on_new_line		 Direct conflict Expression bodies collapse a function to a single line using the => syntax. The second rule enforces multi-line block bodies for control flow. For any single-statement function, one rule will always be violated. prefer_expression_function_bodies always_put_control_body_on_new_line
unnecessary_final
vs
prefer_final_locals		 Direct conflict prefer_final_locals warns whenever a local variable could be marked final but is not. unnecessary_final warns whenever final is present and considered unnecessary. Each rule flags exactly what the other rule requires. unnecessary_final prefer_final_locals
unnecessary_final
vs
prefer_final_in_for_each		 Direct conflict The same issue applies to for-each loop variables. prefer_final_in_for_each requires final on the loop variable; unnecessary_final then flags that very usage as unnecessary. unnecessary_final prefer_final_in_for_each
prefer_foreach
vs
avoid_function_literals_in_foreach_calls		 Direct conflict prefer_foreach encourages using .forEach() instead of a for loop. However, the moment you do that with an inline function, avoid_function_literals_in_foreach_calls flags the function literal inside it. Together, they leave no valid way to write the loop. prefer_foreach avoid_function_literals_in_foreach_calls

Logical redundancies — one rule fully covers what the other already handles

Redundant pair Severity Explanation Reference
hash_and_equals
and
avoid_equals_and_hash_code_on_mutable_classes		 Redundant The first rule requires that == and hashCode always be overridden together. The second rule discourages overriding either on mutable classes. Depending on whether a class is mutable, one rule will always be working against the other. hash_and_equals avoid_equals_and_hash_code_on_mutable_classes
unnecessary_null_comparison
and
dead_null_aware_expression		 Redundant Both rules detect null checks on values that are already known to be non-nullable. Their coverage overlaps significantly, and having both enabled produces duplicate or near-identical warnings for the same piece of code. unnecessary_null_comparison dead_null_aware_expression
type_annotate_public_apis
and
always_specify_types		 Redundant always_specify_types covers the entire codebase, including all public APIs. This makes type_annotate_public_apis completely redundant, as everything it checks is already handled by the broader rule. type_annotate_public_apis always_specify_types
avoid_returning_this
and
cascade_invocations		 Redundant Both rules push towards using Dart cascade notation rather than builder-style method chaining. When both are enabled, they produce overlapping warnings on the same patterns, and can create friction when the builder pattern is intentional by design. avoid_returning_this cascade_invocations
parameter_assignments
and
prefer_final_parameters		 Redundant prefer_final_parameters prevents parameter reassignment by enforcing final at the structural level. With that rule in place, parameter_assignments becomes redundant since the compiler itself blocks the reassignment. Both produce different error messages for the same underlying issue. parameter_assignments prefer_final_parameters

Problematic inclusions — rules that should be removed or reconsidered for this project

Rule Severity Explanation Reference
avoid_web_libraries_in_flutter Wrong for web This rule flags the use of dart:html and related web-only libraries. For a Flutter Web project, accessing these libraries is sometimes necessary and completely legitimate. This rule should be removed from a web-only codebase. avoid_web_libraries_in_flutter
public_member_api_docs Intended for packages This rule requires a documentation comment on every public member. It was designed for authors publishing packages to pub.dev, not for application development. In a typical Flutter app it generates hundreds of warnings on code that will never be consumed as an external API. public_member_api_docs
diagnostic_describe_all_properties Intended for packages This rule requires that every Diagnosticable property be included in debugFillProperties. It is aimed at widget library authors who need rich debug output for their consumers, not at application developers. It adds significant boilerplate to every widget class. diagnostic_describe_all_properties
avoid_classes_with_only_static_members Impractical This rule discourages utility and constants classes, which are a very common and sensible pattern in Flutter apps (such as AppColors or AppStrings). Replacing them with top-level declarations often hurts code organisation in larger projects. avoid_classes_with_only_static_members
one_member_abstracts Impractical This rule warns against abstract classes with only one method. However, single-method interfaces are a standard and well-accepted pattern in dependency injection, repository layers, and interface-segregation design. Removing them purely on this basis would harm architecture. one_member_abstracts
avoid_slow_async_io Not applicable to web This rule targets synchronous file system methods from dart:io such as File.existsSync. These APIs do not exist in Flutter Web. The rule is entirely irrelevant for a web-only project and will never produce a meaningful warning. avoid_slow_async_io
no_default_cases Conflicts with safety Discouraging default in switch statements is only safe when combined with exhaustive enum checks. When this rule is used alongside exhaustive_cases on non-enum types or external values, it can lead to runtime failures that would otherwise be caught by a default branch. no_default_cases exhaustive_cases
lines_longer_than_80_chars Conflicts with formatter The official Dart formatter (dart format) produces lines longer than 80 characters in some valid cases, such as long string literals and URLs. This lint rule will trigger on correctly formatted code, creating a constant source of friction between the formatter and the linter. lines_longer_than_80_chars dart format docs
